# Lifecycle-safe archival and per-start-date flexible inventory

This change adds durable lifecycle/history views, archive-instead-of-delete behavior, per-start-date flexible capacity, and replayable payment/cancellation effects. The recovery model is strongest on the flexible path, where an order ID becomes an inventory claim and cancellation effects are fenced independently from financial settlement. Seven concrete integrity defects remain, including one schema blocker that prevents all paid flexible bookings from being created and recovery gaps that can overcount batch inventory or coupon usage.

Watch for: **[confirmed]** every flexible booking fails Mongoose validation; **[confirmed]** batch finalization can reserve the same seats again after a crash and compensating refunds cannot release that orphaned reservation; **[confirmed]** deleting a coupon during paid finalization archives the aggregate that finalization must claim; **[confirmed]** platform coupon finalization can overrun global and per-user limits.

**Verdict**: NEEDS_CHANGES

## High-level view

**[confirmed]** Flexible inventory is materialized by `(flexAvailabilityId, startDateKey)` and reservation replay is keyed by the payment order, but the `TripBooking` date-key validator rejects the canonical key. Every paid flexible booking therefore rolls back its reservation and enters payment recovery.

**[confirmed]** Batch inventory has no equivalent reservation claim. A crash after incrementing `Batch.bookedSeats` can make the next worker increment the same order again, while compensating refunds only release flexible inventory.

**[confirmed]** Coupon redemption is deferred into required post-insert effects. An in-flight operator coupon can be archived before its claim, and platform claims increment without rechecking eligibility or limits; confirmed booking rows are also published before any required effect succeeds.

**[confirmed]** Flexible capacity updates can partially commit even when the combined request is rejected for an overlapping date range. **[confirmed]** Package suspension also uses an exact end timestamp instead of the inclusive IST business-day boundary used by lifecycle/history classification.

<summary>Issues (8)</summary>

1. **[confirmed] Flexible date-key validator** — `TripBooking` rejects every canonical `YYYY-MM-DD` flexible start key. Correct the regex and validate a real flexible booking document in tests.
2. **[confirmed] Unclaimed batch reservations** — paid-finalization replay can increment batch seats twice, and compensating refund cannot release an orphaned batch increment. Add order-keyed batch reserve/release claims persisted through `PendingOrder`.
3. **[confirmed] In-flight coupon archival** — coupon delete archives a coupon while a charged order still needs to claim it. Return `409` for in-flight references before applying archive/delete.
4. **[confirmed] Premature confirmed booking publication** — a `CONFIRMED` row is visible before required aggregate effects finish. Keep it non-public and non-cancellable until effects complete, or claim effects before publication.
5. **[confirmed] Unbounded platform coupon claims** — finalization increments usage without atomic global/per-user eligibility checks. Add a replay-aware capped claim and a unique per-user redemption claim or transaction.
6. **[confirmed] Partial flexible update on rejection** — capacity writes happen before date-overlap validation, so a `409` can still mutate capacity. Complete validation before the first write and commit related capacity changes atomically.
7. **[confirmed] Package suspension boundary** — active-booking protection stops at the stored end timestamp rather than the end of the inclusive IST date. Compare against IST day start or an end-exclusive business boundary.
8. **[confirmed] State-machine coverage gap** — tests assert fields and exports but never execute reservation, claim, cancellation, or compensation transitions. Add database-backed success, replay, crash, race, and rejection tests.

## Flexible finalization cannot persist its canonical date key

**[confirmed]** `TripBooking.flexStartDateKey` uses `/^\\d{4}-\\d{2}-\\d{2}$/`, which rejects digit-only keys (`models/TripBooking.js:106`). Finalization writes values such as `2026-06-11` near the booking insert (`controllers/tripBookingController.js:1983`), so `TripBooking.create` fails after date inventory has been reserved. The catch releases the reservation, and repeated attempts move the paid order toward refund/reconciliation.

A schema smoke test reproduced `Path 'flexStartDateKey' is invalid (2026-06-11)`. Change the validator to `/^\d{4}-\d{2}-\d{2}$/` and add a model-level test using an actual flexible booking document.

## Batch reservations are not replay-safe or compensatable

**[confirmed]** batch finalization increments `Batch.bookedSeats` with an unkeyed `$inc` (`controllers/tripBookingController.js:1653`). If the process dies after this write and before booking insertion, an expired finalization lease allows the same paid order to increment again, falsely consuming multiple seat allocations.

The refund path cannot repair the leak: `releasePendingFlexReservation` only resolves flexible inventory and parent claims (`controllers/paymentController.js:1128`), and both compensating-refund completion paths call only that helper (`controllers/paymentController.js:1269,1411`). A failed paid batch order remains counted after its payment is refunded.

Add a batch reservation claim keyed by `razorpayOrderId`, persist it on `PendingOrder`, and use the same conditional reserve/retry/release pattern as flexible inventory. This fits the current recovery design more directly than introducing a new transaction boundary.

## Coupon archival can strand an already charged order

**[confirmed]** `deleteCoupon` detects an in-flight `PendingOrder` but uses that result to select archival (`controllers/couponController.js:556-572`) rather than reject the mutation. Archival sets `isActive=false` and `isArchived=true`; required effects then require the quoted coupon to remain active and non-archived and throw when no claim matches (`controllers/tripBookingController.js:1177-1240`).

Return `409` when `inFlight` is true, matching package, batch, and flexible availability deletion. Historical use can still select archive after payment finalization no longer references the coupon.

## Confirmed bookings are visible before required effects complete

**[confirmed]** `createBooking` inserts the row as `CONFIRMED` (`controllers/tripBookingController.js:1983`) and only afterward calls `ensureRequiredBookingEffects` (`controllers/tripBookingController.js:2059`). A coupon race, archived coupon, missing aggregate, or conversation failure leaves a live booking and reserved inventory while `PendingOrder` is retryable or reconciliation-required. User/operator reads and cancellation can act on a row whose payment API still reports finalization pending.

Keep the booking non-public/non-cancellable until required effects complete, or allocate its ID first and claim required aggregates before publishing `CONFIRMED`. At minimum, reads and notifications should require `requiredEffectsState === "COMPLETED"`, with recovery owning the visibility transition.

## Platform coupon claims bypass quote-time limits

**[confirmed]** finalization runs `PlatformCoupon.updateOne({_id, usageClaimKeys: {$ne: effectKey}}, {$inc: {usedCount: 1}})` without checking activity, validity, targeting, `usageLimit`, first-booking eligibility, or `perUserLimit`, and ignores `matchedCount` (`controllers/tripBookingController.js:1245-1249`). Concurrent paid orders can all pass the read-only quote and exceed both global and per-user limits.

Use a replay-aware conditional pipeline with an atomic global-cap predicate and fail when no document matches. Per-user concurrency needs a uniquely keyed coupon/user claim or a transaction; counting bookings before either insert is not a reservation.

## Flexible capacity changes can commit inside a rejected update

**[confirmed]** a request changing both `maxBookings` and dates updates date inventory and the parent under the capacity lease first (`routes/flexibleAvailabilityRoutes.js:442-451`), then checks overlap (`routes/flexibleAvailabilityRoutes.js:454-470`). An overlap returns `409` after capacity has already changed.

Complete ownership, range, overlap, and capacity validation before the first write, then update the parent and materialized inventory together under the lease. Use a transaction where supported.

## Package suspension violates the inclusive IST end date

**[confirmed]** `countFutureOrOngoingLiveBookings` compares the effective end date to exact `now` (`controllers/packageController.js:16-42`). Date-only ends represent the start of that date, so later the same IST day a confirmed booking is omitted even though lifecycle rules keep the end date active through midnight. Operator/admin suspension can deactivate the package during the trip’s final day.

Compare against `getISTDayRange(getISTDateKey(now)).start`, or derive an end-exclusive key and compare it with `now`.

## Contract tests do not execute the state machines

**[confirmed]** recovery tests only assert schema paths and exports (`test/recovery-contract.test.cjs:13-45`), while lifecycle tests cover pure helpers and route order (`test/lifecycle-contract.test.cjs:98`). They never create a flexible booking, replay a reservation, interrupt finalization, archive a coupon during finalization, race coupon limits, or replay cancellation. All eight targeted tests pass despite the main flexible path being impossible.

Add database-backed tests for paid flexible success/replay, batch crash/retry/refund compensation, in-flight coupon delete, platform limit races, cancellation replay, and combined flexible date/capacity rejection. Preserve the existing IST boundary assertions.
