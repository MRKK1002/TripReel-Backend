# Replay-safe booking finalization and lifecycle integrity

This change closes the lifecycle and recovery defects around flexible and batch bookings, coupon claims, publication, cancellation, and confirmation delivery. Paid bookings reserve inventory with stable payment-order identities, remain `PENDING` until required durable effects finish, and publish `CONFIRMED` before notifications begin. Flexible updates validate business-date and capacity boundaries before writes, while strict notifications use durable effect identities. Successful-booking cancellation remains a separate booking-keyed release, and push delivery stays best-effort after durable in-app persistence.

Watch for: **[confirmed]** no remaining concrete correctness defect was found in the reviewed repair scope.

**Verdict**: APPROVED

## High-level view

The payment order owns the pre-booking capacity claim: pre-insert failure and compensating refund release it idempotently, while retry reactivates it exactly once. Once a booking exists, cancellation uses the booking ID as a distinct release effect, preventing either lifecycle from double-decrementing capacity.

Versioned bookings stay in a processing state until package count, coupon claims, conversation creation, and the booking-summary message are durable. The final required-effect update publishes `CONFIRMED`; cancellation rejects incomplete rows, and confirmation delivery only claims published rows.

Platform coupon finalization rechecks activity, validity, targeting, minimums, global capacity, first-booking eligibility, and the per-user cap inside the atomic claim. Cancellation removes active usage once while lifetime audit history remains monotonic.

Combined flexible edits validate overlap and capacity before writing, repeat mutable checks under the capacity lease, and restore child capacities if parent publication fails. Package suspension uses the start of the current IST day, protecting trips throughout their inclusive final day.

Strict confirmation notifications use stable booking/channel/recipient keys under a unique partial index. Durable in-app writes are idempotent across retry; push remains outside the durable completion guarantee.

## Order-keyed reservation claims separate recovery from cancellation

Batch capacity uses an atomic Razorpay-order claim. Active replay leaves `bookedSeats` unchanged, a released claim can be reactivated once after pre-insert compensation, and `PendingOrder` carries the source and claim into both immediate and reconciled refund cleanup. Release occurs only after provider-confirmed refund completion.

Completed-booking cancellation deliberately changes identity domains: inventory is released under the booking ID, with `inventoryReleasedAt` and aggregate release keys fencing replay. The inspected create-failure, retry, compensation, successful insert, and later-cancellation sequences therefore cannot subtract twice.

## Required effects own publication

`TripBooking.create` writes version 1 rows as `PENDING`. `ensureRequiredBookingEffects` applies booking-keyed package and coupon claims, upserts the conversation and summary message, then writes `requiredEffectsState: COMPLETED` with `status: CONFIRMED`. Recovery re-enters this helper before completing `PendingOrder`, including repair of a completed-effects row still marked `PENDING`.

`processCancellationRefund` rejects incomplete version 1 rows. User and operator reads expose their literal `PENDING` state, and confirmation delivery requires both `CONFIRMED` and completed required effects.

## Platform coupon claims preserve quote eligibility under concurrency

The platform claim admits either the existing booking effect or a currently eligible new claim. New claims atomically enforce active/non-archived state, validity, targeting, guest and subtotal minimums, global `usageLimit`, and per-user capacity; counters and history advance only for a new booking key. First-booking coupons also reject prior published bookings and serialize concurrent attempts through per-user claims.

Cancellation resolves the stored coupon ID, requires the booking's usage claim, and uses a release key before decrementing `usedCount`. Active user membership is removed once while lifetime keys and `everUsedCount` remain intact. Operator coupon deletion returns `409` before archive/delete when a matching `PendingOrder` is in flight.

## Flexible edits reject before capacity mutation

The combined update validates range, prices, capacity, overlap, and over-capacity state before the first write, then repeats mutable predicates under the reservation-blocking lease. Materialized capacities move before parent publication; saved parent and child values are restored on failure without requiring transactions.

The flexible date-key validator accepts canonical `YYYY-MM-DD`, with a schema test covering a minimal versioned booking and a noncanonical rejection. Package suspension derives its cutoff from IST day start, matching the end-exclusive lifecycle boundary.

## Durable notification identities close the retry window

Strict user and operator notifications use stable booking/channel/recipient keys; admin fan-out appends each admin ID. The unique partial `Notification.effectKey` index fences races, and duplicate-key recovery returns the winning row.

A crash after persistence but before channel marking retries the same upsert instead of inserting another durable notification. Push remains best-effort after persistence, as intended.
